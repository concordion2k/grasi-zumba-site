# Deployment

This project deploys via **GitHub Actions** to AWS, using **remote Terraform state** and a
**GitHub OIDC** role (no long-lived AWS keys). Region: **us-east-1**.

```
push to main ──> CI (.github/workflows/ci.yml: lint, typecheck, test, build)
            └──> Deploy (.github/workflows/deploy.yml):
                   assume AWS role (OIDC) → terraform apply → sync SPA to S3 → invalidate CloudFront
```

## One-time setup

Do these once, in order. Steps 1–2 need **admin AWS credentials** on your machine
(`aws sso login` or exported keys).

### 1. Bootstrap AWS prerequisites

Creates the state bucket, lock table, GitHub OIDC provider, and the deploy IAM role.

```bash
cd terraform/bootstrap
terraform init
terraform apply            # review, then approve
terraform output deploy_role_arn
```

> If the account already has a GitHub OIDC provider:
> `terraform apply -var create_oidc_provider=false`

### 2. Add the GitHub secret

Repo → **Settings → Secrets and variables → Actions → New repository secret**:

| Name                  | Value                                    |
| --------------------- | ---------------------------------------- |
| `AWS_DEPLOY_ROLE_ARN` | the `deploy_role_arn` output from step 1 |

### 3. Deploy

Push to `main` (or run the **Deploy** workflow manually via _Actions → Deploy → Run workflow_):

```bash
git push origin main
```

The pipeline builds everything, runs `terraform apply` (creating DynamoDB, Lambda, API Gateway,
S3 + CloudFront, etc.), uploads the SPA, and invalidates the CDN. First run takes ~5–15 min
(CloudFront).

### 4. Get the URL & become admin

- The site URL is printed in the deploy job summary, or run from `terraform/`:
  `terraform init -backend-config=backend.hcl && terraform output -raw site_url`
- Open the site, **register with `concordion@mac.com`** — it's in `admin_bootstrap_emails`
  ([terraform/prod.auto.tfvars](terraform/prod.auto.tfvars)), so you're auto-promoted to admin.

## How ongoing deploys work

Every push to `main` runs the **Deploy** workflow, which has two jobs:

1. **verify** — lint, format check, typecheck, tests, build.
2. **deploy** — `needs: verify`, so it only runs if verify passes; then `terraform apply` +
   sync SPA + invalidate CloudFront.

So a failing check **blocks** the deploy. Pull requests run the same checks via `ci.yml`.

## Configuration reference

| What                       | Where                                                                            |
| -------------------------- | -------------------------------------------------------------------------------- |
| Admin emails, region, env  | [terraform/prod.auto.tfvars](terraform/prod.auto.tfvars) (committed, non-secret) |
| Remote state location      | [terraform/backend.hcl](terraform/backend.hcl)                                   |
| Session secret             | auto-generated by Terraform → SSM + Lambda env (never committed)                 |
| Deploy role / state / OIDC | [terraform/bootstrap/](terraform/bootstrap/)                                     |

## Notes

- **Cost:** ~free-tier to a few dollars/month (DynamoDB on-demand, Lambda, API Gateway scale to ~zero).
- **No domain needed** to launch — served on a `*.cloudfront.net` URL. Add a custom domain later
  (ACM cert in us-east-1 + CloudFront alias + DNS); see [terraform/cloudfront.tf](terraform/cloudfront.tf).
- **DynamoDB has `prevent_destroy`** so customer data can't be wiped by an accidental destroy.
- **Rollback:** revert the commit and push — the pipeline redeploys the previous version.
- The deploy IAM role is broad-by-service for simplicity; tighten in
  [terraform/bootstrap/main.tf](terraform/bootstrap/main.tf) later if desired.
